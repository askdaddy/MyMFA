# 架构决策记录（ADR）

本文件记录全部影响架构的决策。每条含**背景 / 决策 / 理由 / 后果**。

状态标记：

- ✅ **已确认** — 用户在需求澄清中明确选择
- ⚠️ **待确认** — 按推荐值写入方案，用户尚未表态，可随时推翻
- 🔧 **技术推导** — 由已确认决策派生的实现选择，未单独征询

变更任何 ✅ 决策需新建 ADR 并标注取代关系，不要就地修改历史记录。

## ADR-001

**技术栈：TypeScript 全家桶** ｜ 状态：✅ 已确认

**背景**：需求要求 Android + iOS + Chrome 扩展三端，桌面端后期。Chrome 扩展必须是 Web 技术，这一点约束了移动端选型。

**决策**：React Native（移动端）+ Chrome MV3 扩展 + 后期 Tauri（桌面端），全部基于 TypeScript，pnpm monorepo 组织。

**理由**：加密、OTP 算法、vault 格式、导入导出解析这些**安全敏感且必须行为一致**的逻辑，可以收敛到一个 TS 核心包，三端共用同一份实现。审计面最小，跨端行为不一致的风险最低。

**放弃的选项**：

- _Flutter_ — 一套代码覆盖移动 + 桌面，UI 一致性最好，但扩展必须用 TS 另写一套核心逻辑，等于两份实现、双份审计。
- _Kotlin Multiplatform_ — 移动端原生性能最好，但扩展需第三套实现，总量最大。
- _Flutter + 共享 Rust/WASM 核心_ — 安全性与性能最优，但工具链复杂，需同时掌握 Dart + Rust + TS。

**后果**：

- ➕ 核心逻辑一次实现三端复用
- ➖ RN 的原生体验与性能略逊于 Flutter
- ➖ **Hermes 不支持 WASM**，移动端 Argon2id 必须走原生模块，无法复用 Web 侧的 `hash-wasm`（这是三端唯一无法共享的实现，见 ADR-009 后果）
- ➖ UI 组件层无法跨端复用，RN 与 Web 各写一套

## ADR-002

**数据同步：纯本地** ｜ 状态：✅ 已确认

**背景**：多设备（尤其手机 ↔ 扩展）如何共享同一份密钥库。

**决策**：不做云同步、不建后端、不做账号体系。V1 通过导出/导入加密文件迁移；V2 增加局域网配对直连传输。

**理由**：不碰用户明文、无需后端运维、无合规责任、成本最低，且"密钥永不离开用户设备"本身就是可信卖点。

**放弃的选项**：云盘同步文件（iCloud/Drive/WebDAV）、自建账号 + 云同步服务、纯局域网 P2P 实时同步。

**后果**：

- ➕ 零后端成本，无隐私合规负担
- ➕ 无冲突解决问题（不存在多写方）
- ➖ 手机与扩展之间的日常体验差，每次变更需手动迁移
- ➖ V2 局域网配对会遇到 Chrome 混合内容与 PNA 限制，需重新评估权限模型（见 [chrome-extension.md §6.2](chrome-extension.md#62-v2局域网配对)）

## ADR-003

**预提示形态** ｜ 状态：✅ 已确认

**背景**：预提示是本产品的差异化功能。"显示未来一个时间点的验证码"有多种呈现方式，需明确语义。

**决策**：当前周期的码作为主体大字显示，**下一周期的码缩小显示在当前码正下方，始终可见**（无需点击展开）。

**理由**：用户在需求澄清中明确选择此形态。始终可见换来"提前复制、零额外交互"的效率，适配只接受下一个时间窗的服务。

**放弃的选项**：始终并排等大显示、点击/长按才显示、可自定义未来偏移量、逐条目开关。

**后果**：

- ➕ 交互成本为零
- ➖ 屏幕共享与旁人窥视时暴露面翻倍 → 用防截屏 + 进入后台遮罩缓解（[features.md §7](features.md#7-安全相关的-ui-要求)）
- ➖ 每行每 tick 需 2 次 HMAC，必须配合列表虚拟化只对可见行计算
- ➖ **HOTP 没有"下一周期"概念**，需显示 `counter+1` 并明确标注，否则用户会误以为它会随时间失效（[features.md §1.2](features.md#12-预提示语义核心差异点)）

## ADR-004

**令牌范围：TOTP + HOTP** ｜ 状态：✅ 已确认

**背景**：MFA App 可支持的令牌类型很多，范围直接决定实现与测试工作量。

**决策**：V1 只支持 TOTP（RFC 6238）与 HOTP（RFC 4226）。导入侧兼容主流 App 格式。

**放弃的选项**：Steam（非标准 TOTP 变体）、Yandex、mOTP、企业级 SAML/OIDC 集成。

**后果**：

- ➕ 算法实现面小，测试向量权威（RFC 官方）
- ➖ Steam 用户群体不小，未来若要支持需在 `packages/otp` 增加变体，并处理其 5 字符字母数字码的特殊展示
- ➖ 企业场景完全不覆盖

## ADR-005

**Chrome 扩展范围：显示 + 域名绑定置顶** ｜ 状态：✅ 已确认

**背景**：扩展可以做到什么程度，直接决定权限模型与审查难度。

**决策**：扩展提供列表显示、搜索、点击复制、**域名绑定自动置顶**、导入导出、条目基础编辑。**不做**自动填充到网页输入框，**不注入** content script。

**理由**：自动填充需处理各站点千差万别的 DOM、申请更宽权限、安全审查面显著变大，而收益（省一次粘贴）有限。域名绑定置顶以极低成本解决了"打开网站要翻找条目"这个真实痛点。

**后果**：

- ➕ 权限极简（`storage` / `activeTab` / `clipboardWrite` / `alarms`，**零 `host_permissions`**），商店审核快、用户安装转化率高
- ➕ 不接触页面 DOM，无脚本冲突与注入风险
- ➖ 用户仍需手动粘贴验证码
- ➖ 若未来做自动填充，权限模型需大幅重做（见 [chrome-extension.md §7](chrome-extension.md#7-若未来要做自动填充)）

## ADR-006

**安全模型：强制主密码 + 可选生物识别** ｜ 状态：✅ 已确认

**背景**：密钥库的解锁与防护做到哪一层。

**决策**：创建 vault 时**必须**设置主密码，之后可用 Face ID / 指纹 / Windows Hello 快捷解锁。生物识别是主密码的**快捷路径而非替代品**。

**放弃的选项**：主密码可选（允许无密码 vault）、额外支持硬件密钥（YubiKey / WebAuthn PRF）派生。

**后果**：

- ➕ 不存在明文 vault 泄露面
- ➕ 与 Aegis 的用户心智一致
- ➖ 用户忘记主密码则数据**完全不可恢复**，必须在创建流程中强告知，且不提供任何后门
- ➖ 扩展端无生物识别能力，每次浏览器重启都需输主密码
- 🔧 派生出 ADR-011 的双层密钥模型（生物识别作为 DEK 的一种包裹方式，架构上天然可扩展到硬件密钥）

## ADR-007

**导出兼容范围** ｜ 状态：✅ 已确认

**背景**：导入侧已定为兼容主流格式；导出侧要做到什么程度。

**决策**：导出覆盖 **自有加密 vault + 自有明文备份 + Aegis 明文 + Aegis 加密 + otpauth URI 文本 + 批量二维码 + Google Authenticator 迁移二维码**。

**理由**：完整的导出矩阵让用户能自由迁出，这本身是信任建设——用户不怕被锁死在本 App 里。

**后果**：

- ➕ 双向迁移能力最强
- ➖ **需实现 scrypt**（Aegis 加密导出用），而自有 vault 用 Argon2id → `packages/crypto` 需同时提供 Argon2id / scrypt / PBKDF2 三种 KDF
- ➖ GA 迁移二维码的 protobuf 无官方规范，需对照真机扫描验证，且需处理分片
- ➖ 导出到通用格式必然丢失 `sites` / `usageCount` / `favorite` 等字段，**必须在 UI 展示字段降级表**（[transfer.md §3.1](transfer.md#31-字段降级表)）
- ➖ 测试工作量最大的一块

## ADR-008

**图标：首字母色块** ｜ 状态：✅ 已确认

**背景**：条目的服务商图标如何处理。

**决策**：**不集成任何品牌图标库**，用 `issuer` 首字母 + 哈希映射的固定色板生成色块。

**理由**：零依赖、零许可证风险、零包体积、零图片加载性能问题。

**后果**：

- ➕ 无 SVG 图标集的许可证与体积负担
- ➕ 实现成本极低
- ➖ 视觉识别度明显不如 Aegis 的真图标，长列表中定位速度较慢 → 靠搜索、tag 筛选、排序弥补
- 🔧 哈希函数必须稳定且跨端一致（用 FNV-1a 类确定性哈希，不用带随机种子的）
- 🔧 首字符提取需正确处理 Unicode（`Array.from(s)[0]`，避免代理对被截断）
- ➕ 未来若要加图标，只需在 Entry 增加可选 `icon` 字段并回退到色块，不破坏现有 vault

## ADR-009

**KDF 选型：Argon2id（而非 Aegis 的 scrypt）** ｜ 状态：✅ 已确认（2026-09-24）

**背景**：自有 vault 的密钥派生函数选择。原为推荐默认值，已于 2026-09-24 由用户确认采纳。

**决策**：Argon2id，参数 `m = 64 MiB`、`t = 3`、`p = 4`、`salt = 16B`、输出 32B。全部参数写入 vault 文件头，只允许上调不允许下调。

**理由**：

1. Argon2id 是 2015 年 PHC 冠军，抗 GPU/ASIC/侧信道均优于 scrypt，是当前业界推荐首选。
2. **更关键**：它在 Web 端有成熟的 WASM 实现（`hash-wasm`），能与移动端原生实现保持**同一算法**，避免"两套 KDF"的审计面。若选 scrypt，Web 侧同样需要额外实现。

**放弃的选项**：scrypt（Aegis 所用）、PBKDF2（WebCrypto 原生支持，但抗 GPU 能力弱于前两者）。

**后果**：

- ➖ **移动端无法复用 WASM**（Hermes 不支持），必须写原生模块：Android argon2-jvm、iOS libsodium `crypto_pwhash`
- ➖ **跨端一致性成为本项目最大技术风险**：三套不同实现必须字节级一致，否则会出现"手机加密的 vault 插件打不开"这类致命问题 → 强制在 **M0 阶段**完成验证，未通过不得开始 vault 层实现（[testing.md §3](testing.md#3-跨端加密一致性测试最高优先级)）
- ➖ 低端 Android 设备派生耗时可能达 1–2 秒，需在 M3 实测
- ➖ 导入 Aegis 加密备份 + 导出 Aegis 加密格式**仍需实现 scrypt**，Argon2id 并没有省掉这个工作量
- ➕ 参数写入文件头，未来上调不破坏旧文件

## ADR-010

**加入时钟校准功能** ｜ 状态：✅ 已确认（2026-09-24）

**背景**：用户原始需求列表中没有此项，原为推荐默认值，已于 2026-09-24 由用户确认采纳。

**决策**：提供「与服务端时间校准」功能，通过 HTTPS 响应头 `Date` 计算 `clockOffsetSeconds` 存入 settings，TOTP 生成时补偿；偏差 > 5 秒时列表顶部常驻提示。

**理由**：TOTP 完全依赖系统时间。手机时间偏差 30 秒会导致**全部**验证码失效，而用户几乎不可能自行诊断出是时钟问题——只会认为"这个 App 算的码是错的"并卸载。这是可用性上的高价值低成本项，Aegis 也提供。

**后果**：

- ➕ 显著降低一类难以自查的失败模式
- ➖ 需要内置 2–3 个可信时间端点并做失败回退，具体端点待 M6 确认
- ➖ 校准请求会泄露用户 IP 与使用时间给该端点 → 应使用无关联性的公共端点，且在设置中说明；用户可关闭
- ➖ 是**本地补偿**，不修改系统时间（无权限，也不应越权）

## ADR-011

**双层密钥模型（DEK / KEK）** ｜ 状态：🔧 技术推导

**背景**：由 ADR-006（生物识别作为快捷路径）派生。

**决策**：分离数据加密密钥与密钥加密密钥。

```
主密码 → Argon2id → KEK（仅存内存，用后清零）
DEK（随机 32B）→ 被 KEK 包裹 → wrappedMasterKey 写入 vault 文件头
DEK           → 被设备安全密钥包裹 → biometricWrappedDek 仅存设备安全存储
DEK           → 加密 vault 明文
```

**理由**：

1. **改主密码只需重新包裹 DEK**，O(1) 而非重加密全库的 O(n)。
2. 生物识别是主密码的快捷路径而非替代品，两条路径互不依赖。
3. 未来扩展新解锁方式（硬件密钥 / WebAuthn PRF / 社交恢复）只是增加一种包裹方式，数据层零改动。
4. 撤销某条路径很干净（如用户删除指纹，只删 `biometricWrappedDek`，vault 文件不受影响）。

**后果**：

- ➕ 密钥管理灵活，扩展性好
- ➖ 比"主密码直接派生 vault 密钥"多一层间接，实现与调试复杂度略增
- 🔧 **硬约束**：`biometricWrappedDek` 绝不进入 vault 文件、导出内容或任何迁移产物，它是设备本地属性
- 🔧 Android 需处理 `KeyPermanentlyInvalidatedException`（生物特征集合变更），静默回退主密码路径

## ADR-012

**手动排序用 fractional indexing** ｜ 状态：🔧 技术推导

**背景**：需要支持拖拽手动排序，且 vault 是全量加密文件。

**决策**：条目带 `position` 字符串键，字典序即显示顺序；插入时生成介于前后两者之间的新键。键长退化超阈值时整体重排一次。

**理由**：数组下标在插入时需重写后续全部条目，导致 vault 产生巨大差异并触发不必要的全量重加密；整数 position 会耗尽间隙。fractional index 让单次拖动只改一个条目。

**后果**：

- ➕ 拖拽操作的写入量恒定
- ➖ 需引入或实现 fractional index 生成逻辑（有成熟小库可用，也可自实现）
- 🔧 排序稳定性：无论何种主排序，二级键恒为 `issuer + account`，避免同值条目每次刷新随机换位（[features.md §3](features.md#3-排序)）

## ADR-013

**Tag 为全局实体** ｜ 状态：🔧 技术推导

**背景**：需求要求给每个密码打 tag。

**决策**：`Tag` 是 vault 顶层的独立实体（id / name / color / position），Entry 通过 `tagIds` 引用。

**理由**：Aegis 的 tag 是 Entry 上的字符串形式，重命名标签需要遍历批量改写全部条目。全局实体让重命名/改色/删除只需改一处，也让标签栏排序与配色成为可能。

**后果**：

- ➕ 标签管理操作 O(1)
- ➖ 需维护引用完整性（删除标签时清理所有 Entry 的 `tagIds`）
- 🔧 导入 Aegis 时需把字符串 tag 转换/映射为全局 Tag 实体，同名合并

## ADR-014

**secret 存原始字节而非 base32** ｜ 状态：🔧 技术推导

**背景**：`otpauth://` URI 与多数 App 的导出格式使用 base32 字符串。

**决策**：vault 内 `Entry.secret` 存 **base64 编码的原始字节**。base32 只出现在导入解析与用户手动输入的场景。

**理由**：base32 是传输编码，不是密钥本体。若存 base32 字符串，各端解码实现对 padding 缺失、大小写、`0/O` 与 `1/I` 混淆字符的容错处理若有差异，会导致**同一个 secret 在不同设备算出不同验证码**——这是最难排查的一类 bug。

**后果**：

- ➕ 消除跨端 base32 解码差异
- ➖ 导出到 otpauth URI 时需转回 base32（不带 padding）
- 🔧 base32 编解码集中在 `packages/otp` 一处实现，需覆盖容错用例测试

## ADR-015

**扩展零 host_permissions** ｜ 状态：🔧 技术推导

**背景**：由 ADR-005（不做自动填充）派生。

**决策**：扩展只申请 `storage` / `activeTab` / `clipboardWrite` / `alarms`，`host_permissions` 留空，不注入 content script。读取当前页域名走 `activeTab`。

**理由**：`activeTab` 在用户点击扩展图标时授予当前标签页的一次性访问权，恰好匹配"打开 popup 时才知道当前站点"的场景，无需常驻宽权限。

**后果**：

- ➕ 权限审查简单，商店审核快，用户信任度高
- ➖ **与 V2 局域网配对冲突**：从扩展页 `fetch` 到 `http://192.168.x.x` 需要 host 权限，且受 Chrome PNA 策略限制 → V2 需改用 `optional_host_permissions` 按需申请私有网段，且必须先做原型验证（[chrome-extension.md §6.2](chrome-extension.md#62-v2局域网配对)）

## ADR-016

**产品名 MyMFA、npm scope `@askdaddy`、托管 GitHub** ｜ 状态：✅ 已确认（2026-09-24）

**背景**：M0 阶段 0 需要确定包命名空间才能建立 monorepo；`iloop` 依赖 `git remote` 路由 CLI，需先定托管平台。

**决策**：

- 产品名 **MyMFA**，仓库名与之对齐
- npm scope **`@askdaddy`**，核心包命名为 `@askdaddy/otp`、`@askdaddy/crypto`、`@askdaddy/vault`、`@askdaddy/transfer`、`@askdaddy/domain`
- 代码托管 **GitHub**，Issue 操作走 `gh` CLI

**理由**：scope 与用户 GitHub 账号一致，便于将来发布到 npm 时不需要改名；GitHub 的 Actions 提供 macOS runner，这是验证 iOS 侧 Argon2id 实现（[ADR-009](decisions.md#adr-009) 后果）的必要条件——GitLab 与 Gitea 的自建 runner 通常没有 macOS 机器。

**后果**：

- ➕ 包名一次到位，避免后期批量替换 `package.json` 与 import 路径
- ➕ CI 可在 macOS runner 上跑 iOS 原生 Argon2id 一致性验证
- ➖ `@askdaddy` scope 下的包若发布到 npm 需先在该 scope 下创建 organization
- 🔧 `AGENTS.md` §3 的目录结构中包名需按此 scope 落地

## ADR-017

**`schemaVersion` 提升为容器头部明文字段** ｜ 状态：🔧 技术推导（2026-09-24）

**背景**：原 [vault-format.md §1.1](vault-format.md#11-加密容器) 规定 `data` 加密时以 `format` / `version` / `schemaVersion` 作 GCM 的 AAD（用于绑定头部、防篡改后仍能解密），但同一节给出的容器头部**只有** `format` 与 `version`，`schemaVersion` 仅存在于加密后的明文里。落地 `packages/vault`（GitHub Issue #3）时暴露出三个无法同时满足的要求：

1. 读取端必须在解密前**重建**写入端用过的 AAD，而 `schemaVersion` 在解密前不可见。若改用读取端自己的编译期常量，AAD 退化为恒定值，头部篡改保护形同虚设；若逐个候选试解密，则引入未定义的试探循环。
2. 高于当前支持值的 `schemaVersion` 必须"不尝试解析"即拒绝，而解析它需要先解密。
3. 拒绝一个用不了的文件之前先跑一次 Argon2id（`m=64MiB`，低端 Android 上 1–2 秒）是纯粹的浪费。

**决策**：

- 容器头部新增顶层明文字段 `schemaVersion`，与 `version` 并列；加密与未加密两种变体对称携带。
- 明文 schema（[§2](vault-format.md#2-明文-schema)）**保留** `schemaVersion` 不变；解密后必须校验头部值与明文值相等，不等即拒绝。
- AAD 布局维持 `utf8Encode(\`${format}\n${version}\n${schemaVersion}\`)`，三个值全部取自头部。
- 读取流程的检查顺序固化为契约：JSON 合法性 → `format` → `encrypted` → 版本 → 参数降级检查，**这五步任一失败都不得调用 KDF 或 AEAD**。
- **不递增容器 `version`**：`packages/vault` 尚未实现，世界上不存在任何 `.mfavault` 文件，这是对 v1 的发布前修订而非 v1→v2 的破坏性变更。

**理由**：三处失败模式同源——决策所需的元数据被放在了需要该决策才能打开的盒子里。把版本信息提到头部是格式设计的常规做法（SQLite、ZIP、PGP 都在明文头部放版本），代价是多一个必须与明文保持一致的字段，收益是 AAD 可重建、高版本可零成本拒绝。头部字段本身受 GCM 认证保护，篡改即解密失败，因此提升可见性不削弱安全性。

**后果**：

- ➕ AAD 的三端字节级对齐有了确定的输入来源，不再依赖"读取端猜"
- ➕ 未来版本的文件可在不消耗 Argon2id 的前提下被拒绝，错误提示更准确（"请升级 App" 而非 "文件损坏或密码错误"）
- ➖ 头部与明文各有一份 `schemaVersion`，必须做相等性校验；漏做会让迁移链与容器封装分头演化
- 🔧 [vault-format.md](vault-format.md) §1.1 / §1.2 / §2 / §4 已同步修订；`packages/vault` 的容器类型与读写路径按此实现

## ADR-018

**第三方加密备份的兼容 KDF 豁免（scrypt / PBKDF2）** ｜ 状态：✅ 已确认（2026-09-28，用户显式授权）

**背景**：[ADR-007](#adr-007) 与 [transfer.md §5](transfer.md#5-加密备份的密钥输入) 要求 `packages/crypto` 同时提供 Argon2id / scrypt / PBKDF2 三种 KDF，以兼容 Aegis 加密备份（scrypt）与 2FAS / Raivio 加密备份（PBKDF2）。落地 `packages/transfer`（GitHub Issue #4）时发现这与 `AGENTS.md` 的两条安全红线**按字面直接冲突**：

- §5.1「**禁止**自研加密算法、自研 KDF、自研 AEAD。**只允许使用 Argon2id + AES-256-GCM**」
- §5.2「优先使用平台原生能力…**必需的 WASM 仅限 Argon2id 一处**」

而 `AGENTS.md` 开篇规定「与 `docs/` 冲突时，以本文件的**安全红线**为准」。按此优先级，Aegis 加密导入 / 加密导出与 2FAS / Raivio 加密导入四条路径全部不可实现，ADR-007 的导出矩阵直接落空。

**决策**：

1. **自有 vault 的加密算法白名单不变**：仍然只有 Argon2id（KDF）+ AES-256-GCM（AEAD）。§5.1 的立法意图是锁死自有格式，这一点**不放宽**。
2. **新增一条边界明确的豁免**：scrypt 与 PBKDF2 **仅允许**出现在「读取或写出**第三方**加密备份格式」的兼容路径上，且必须满足全部四个条件：
   - KDF 参数（`N` / `r` / `p` / `iterations` / `salt` / `keyLength`）**一律取自备份文件自身头部**，禁止使用本 App 默认值（§5.1「禁止下调 Argon2id 参数」的基线检查不适用于此路径——那是别人的文件，参数不由我们定）
   - 派生出的密钥**只用于解开该第三方容器**，禁止参与自有 vault 的任何密钥派生、包裹或认证
   - 兼容路径**禁止**被自有 vault 的读写路径调用（`packages/vault` 不得依赖它）
   - 仍然禁止自研：scrypt 与 PBKDF2 的实现必须来自既有依赖，不得手写
3. **§5.2 的 WASM 限制改述为「仅限 `hash-wasm` 一处」**，而非「仅限 Argon2id 一处」。

**理由**：

- 冲突是**措辞层面**的，不是技术层面的。已装依赖 `hash-wasm@4.12.0` 本身就同时导出 `scrypt`（入参 `password / salt / costFactor / blockSize / parallelism / hashLength`）与 `pbkdf2`（入参 `password / salt / iterations / hashLength / hashFunction`），因此本豁免**不新增任何依赖**，也**不引入第二处 WASM**——§5.2 限制 WASM 的立法意图（收敛审计面）实际上从未被突破，被突破的只是「那一个模块里只准用一个算法」这层字面表述。
- scrypt 的参数模型与 Aegis 备份头部的 `N / r / p` 一一对应，PBKDF2 的 `iterations` 与 2FAS / Raivio 头部一一对应，因此「参数取自文件头」这一条可直接满足，不需要任何猜测或降级。
- 不豁免的替代方案是砍掉全部第三方加密备份兼容，代价是用户从 Aegis 迁移时**必须先自行导出明文备份**——而 Aegis 的明文导出本身带风险提示，等于把风险转嫁给用户，与「方便用户从别的 app 迁移数据」的原始需求相悖。

**放弃的选项**：

| 选项                                               | 放弃理由                                                                                                                                                                               |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 红线一字不改，砍掉全部加密兼容路径                 | 违背用户原始需求；ADR-007 需整段推翻；用户被迫经手中文明文备份，风险反而上升                                                                                                           |
| 只豁免 PBKDF2（WebCrypto 原生支持），不豁免 scrypt | PBKDF2 确实不触碰 §5.2，但 Aegis 是导入矩阵中**置信度最高、用户量最大**的来源，砍掉它收益最小；且 scrypt 走 `hash-wasm` 与 PBKDF2 走 WebCrypto 会形成两套 KDF 注入路径，审计面反而更大 |
| 手写纯 TS 的 scrypt                                | 直接违反 §5.1「禁止自研 KDF」的**实质**意图（不是措辞），且无法与参考实现做一致性对照                                                                                                  |

**后果**：

- ➕ ADR-007 的导出矩阵完整保留，用户可从 Aegis / 2FAS / Raivio 的加密备份直接迁入
- ➕ 无新依赖、无第二处 WASM，`AGENTS.md` §5.2 的审计面收敛目标不变
- ➖ `packages/crypto` 的 `KdfProvider` 契约必须扩展：`name` 当前被钉成字面量 `'argon2id'`（`packages/crypto/src/providers.ts:8`），容纳第二种 KDF 需要改这个接口，而它已被 `packages/vault` 的实现与 177 个测试依赖 → **跨包契约变更**，须在 Issue #4c 中先改文档再改代码
- ➖ scrypt 在 Web 端仍需 WASM（WebCrypto 不提供 scrypt），移动端 M3 需另找原生实现（Android `org.bouncycastle` / iOS `CommonCrypto` 均无 scrypt，大概率走 libsodium 的 `crypto_pwhash_scryptsalsa208sha256`）→ 新增一条跨端一致性风险，须纳入 M3 前的验证清单
- 🔧 `AGENTS.md` §5.1 / §5.2 的措辞修订由**开发**在 Issue #4c 的 plan 覆盖下执行（PM 可写区域仅 `docs/`，无权改根级 `AGENTS.md`）；修订授权来自用户于 2026-09-28 的显式确认
- 🔧 [transfer.md §5](transfer.md#5-加密备份的密钥输入) 与 [security.md §3](security.md#3-加密算法与参数) 已同步补上豁免边界

## ADR-019

**第三方格式 golden test 的权威来源改为各 App 开源仓库 schema** ｜ 状态：✅ 已确认（2026-09-28，用户显式授权）

**背景**：[testing.md §5](testing.md#5-导入-golden-test) 与 [transfer.md](transfer.md) 文档头均规定「第三方格式字段名基于公开资料与社区逆向，不可直接作为实现依据；M2 阶段必须先用**真实 App 导出样本**校准字段名，再固化 golden test」，[architecture.md §7](architecture.md#7-关键架构风险) 的风险 R4「导入格式字段名与文档不符」概率标注为**高**、后果「导入静默丢数据」、缓解措施「以真实样本为准建立 golden test，不信任二手资料」。落地 Issue #4 时确认：用户未提供任何真实样本，`AGENTS.md` §5.3 又禁止提交真实备份，故该缓解措施在本闭环内**不可执行**。

**决策**：

1. golden test 的字段名权威来源改为**各 App 开源仓库中的 schema 定义**（Aegis / 2FAS / FreeOTP / Ente Auth 均为开源项目，其源码是一手资料而非社区逆向）与**官方文档**（Bitwarden / 1Password 的 CSV 列结构）。
2. 每个夹具文件必须在文件头注明其来源（仓库路径 + commit / tag，或文档 URL），并显式标注「依据 schema 定义构造，非真实 App 导出」。
3. 真机校准**降级为后续跟进项**，不阻塞 M2：新增独立 Issue 跟踪「用真实 App 导出样本回归校验已实现的解析器」，在具备设备与样本时执行。
4. 无权威来源可用的格式（`transfer.md` 矩阵中置信度标注为「低」的 LastPass）不实现解析器，改为在导入界面提示用户走**通用 CSV 手动列映射**路径。
5. GA 迁移二维码的 protobuf **解码**侧可按公开的 `MigrationPayload` 定义实现并自验；**编码**（导出）侧的真机扫描验证同样降级为后续跟进项，且在完成前 UI 必须标注「未经 Google Authenticator 真机验证」。

**理由**：R4 的实质风险是「依据博客文章或社区逆向的字段名写解析器，导致静默丢数据」。开源仓库的 schema 定义**不是**二手资料——它就是产生真实导出文件的那段代码，与真实样本的信息量等价，且不受 `AGENTS.md` §5.3 的提交禁令约束。把缓解措施从「真实样本」改为「一手 schema」保留了 R4 的防护强度，同时解除了对设备与用户隐私数据的依赖。

**放弃的选项**：等用户提供真实脱敏样本后再开工（#4 无限期阻塞，且用户需自行完成脱敏，反而增加真实 secret 外泄的操作面）；只做完全可控的两种格式（MVP 的导入兼容能力大幅缩水，违背原始需求）。

**后果**：

- ➕ #4 解除阻塞，M2 可推进
- ➕ 夹具来源可追溯，评审时能直接核对上游 schema
- ➖ 仍无法覆盖「App 实际写出与其 schema 定义不一致」这一类缺陷（例如某版本 Aegis 的导出器有 bug）→ 由第 3 条的真机校准跟进项兜底，**风险未被消除，只是后移**
- ➖ LastPass 导入降级为手动列映射，需在导入界面文案中说明
- 🔧 [testing.md §1 / §5](testing.md#5-导入-golden-test)、[transfer.md](transfer.md) 文档头与 §7、[architecture.md §7](architecture.md#7-关键架构风险) 的 R4 行已同步修订；夹具目录路径一并订正为 `packages/transfer/src/__fixtures__/`，与 `.gitignore` 的例外规则和既有各包的 `src/__tests__/` 结构对齐
