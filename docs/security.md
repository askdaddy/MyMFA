# 安全设计

> 关联决策：[ADR-006 安全模型](decisions.md#adr-006)、[ADR-009 KDF 选型](decisions.md#adr-009)、[ADR-011 双层密钥](decisions.md#adr-011)、[ADR-017 容器头部 `schemaVersion`](decisions.md#adr-017)、[ADR-018 兼容 KDF 豁免](decisions.md#adr-018)
> 状态：设计基线。`packages/otp`、`packages/crypto`、`packages/crypto-web` 已落地；Web 端一致性 gate（§4）已达成，移动端部分待 M3

本 App 持有用户的第二因素。密钥库泄露的后果等同于账户被完全接管，因此安全设计的优先级高于一切功能特性。

## 1. 威胁模型

**假设攻击者能够**：

- 获取用户设备上的 vault 文件（备份外泄、设备丢失、恶意同步软件）
- 获取用户导出的明文备份文件
- 在导入路径上投喂恶意构造的文件（畸形 protobuf / 超长字段 / 深层嵌套）
- 通过屏幕共享、录屏、最近任务卡片窥视验证码
- 在同一局域网内嗅探或主动连接迁移通道

**不假设防御**：

- 设备已 root/越狱且攻击者有运行时内存读取能力（此时任何本地 App 都无法保护密钥）
- 用户主密码强度极低（只能提示，不能强制）
- 键盘记录器已植入

## 2. 双层密钥模型

不直接用主密码派生 vault 加密密钥，而是分离 **DEK** 与 **KEK**：

```
主密码 ──Argon2id(salt, m=64MiB, t=3, p=4)──→ KEK（32B，仅存于内存，用后立即清零）
DEK（32B，密码学安全随机，永不直接暴露给用户）
       └── AES-256-GCM(KEK) 包裹 ──→ wrappedMasterKey，写入 vault 文件头
       └── 设备安全密钥包裹       ──→ biometricWrappedDek，仅存设备安全存储
DEK ── AES-256-GCM ──→ vault 明文（gzip(JSON)）
```

这样设计带来四个直接收益：

1. **修改主密码只需重新包裹 DEK**，无需重加密整个 vault，O(1) 而非 O(n)。
2. **生物识别是主密码的快捷路径而非替代品**。设备安全存储里存的是被生物特征保护的密钥所包裹的 DEK 副本；生物识别失败或变更后，主密码路径依然完整可用。
3. **未来扩展新解锁方式**（硬件密钥 / WebAuthn PRF / 社交恢复）只是增加一种 DEK 包裹方式，数据层零改动。
4. **撤销某条路径很干净**。例如用户在设备上移除了指纹，只需删除 `biometricWrappedDek`，vault 文件不受影响。

**关键约束**：`biometricWrappedDek` 绝不进入 vault 文件、导出内容或任何同步产物。它是设备本地属性。

### 2.1 生物识别实现要点

| 平台        | 机制                                                                                          |
| ----------- | --------------------------------------------------------------------------------------------- |
| iOS         | Keychain 存储，访问控制设为 `kSecAccessControlBiometryCurrentSet`，生物特征集合变更时自动失效 |
| Android     | BiometricPrompt（Class 3 / Strong 级别）解锁 Keystore 中的非导出密钥，用该密钥包裹 DEK        |
| Chrome 扩展 | 无生物识别能力，每次会话必须输入主密码；解锁态由 `chrome.storage.session` 在浏览器会话内维持  |

Android 侧需处理 `KeyPermanentlyInvalidatedException`（用户新增/删除生物特征），此时静默回退到主密码路径并清除失效的包裹副本。

### 2.2 明文清零的能力边界（不要过度承诺）

`AGENTS.md` §5.4 要求"明文 vault 在内存中使用后主动清零，不得依赖 GC"。在 JavaScript 里这条要求**只能部分达成**，必须区分两类数据：

| 类别     | 具体内容                                              | 能否清零 | 原因                                                                   |
| -------- | ----------------------------------------------------- | -------- | ---------------------------------------------------------------------- |
| 可清零   | KEK、DEK、解密得到的密文/明文字节、gzip 中间缓冲区    | ✅       | 都是 `Uint8Array`，`fill(0)` 就地覆写底层 `ArrayBuffer`                |
| 不可清零 | `JSON.parse` 之后对象图里的 `secret`、`note` 等字符串 | ❌       | JS 的 `string` 不可变，无法原地覆写；GC 何时回收不可控，且可能已有副本 |

因此本项目的实际承诺是：

- **所有 `Uint8Array` 形态的密钥与中间字节，在最后一次使用后立即 `fill(0)`**，包括**异常路径**——解密失败、认证失败、schema 校验失败时同样必须清零，不能把清零责任留给调用方。
- 已解锁的 `VaultData` 对象图**无法**清零。缓解措施属于 app 端职责：最小化其存活期（用完即 `lock()` 释放引用）、不做长期缓存、不写入任何持久化位置、不进入日志与崩溃上报。
- 可验证的断言只有**行为层面**的：`lock()` 之后访问任何成员都抛错；注入一个记录缓冲区引用的测试替身，可断言中间 `Uint8Array` 在流程结束后全为零。**不能**断言堆上的字符串已被覆盖——任何声称做到这一点的表述都是错的。

这条边界不削弱威胁模型：§1 已明确"不假设防御设备已 root 且攻击者具备运行时内存读取能力"。清零针对的是**进程正常存活期间的意外残留**（内存快照、崩溃转储、被同页面其他脚本读到），而不是对抗有内存读取能力的攻击者。

## 3. 加密算法与参数

| 项     | 选型        | 参数                                                        |
| ------ | ----------- | ----------------------------------------------------------- |
| KDF    | Argon2id    | `m = 64 MiB`、`t = 3`、`p = 4`、`salt = 16B 随机`、输出 32B |
| AEAD   | AES-256-GCM | `nonce = 12B 随机`、`tag = 16B`                             |
| 随机数 | 平台 CSPRNG | WebCrypto / SecureRandom / arc4random                       |
| 压缩   | gzip        | 加密**前**压缩明文                                          |

**参数策略**：

- 所有参数写入 vault 文件头，读取时以文件头为准，不使用硬编码值。这样未来上调参数不会破坏旧文件。
- **只允许上调，不允许下调**。下调需通过 ADR 记录并说明理由（见 `AGENTS.md` §5.1）。
- Argon2id 的 `m=64MiB` 是移动端与抗 GPU 暴破之间的折中。低端 Android 设备上派生耗时可能达 1–2 秒，需在 M3 实测并考虑是否提供"高性能模式"降级选项（若提供，必须默认关闭且显著警告）。

**为什么是 Argon2id 而非 scrypt**：Aegis 使用 scrypt。本项目选 Argon2id 是因为它在 Web 端有成熟的 WASM 实现（`hash-wasm`），能与移动端原生实现保持同一算法，减少"两套 KDF"的审计面。代价是导入 Aegis 加密备份时仍需单独实现 scrypt 解密——但那是**兼容路径**，不影响自有 vault 的安全模型。详见 [ADR-009](decisions.md#adr-009)。

scrypt 与 PBKDF2 触碰 `AGENTS.md` §5.1 / §5.2 的字面禁令，其豁免由 [ADR-018](decisions.md#adr-018) 规定，边界是硬性的：**自有 vault 的算法白名单不变**（仍只有 Argon2id + AES-256-GCM），scrypt / PBKDF2 只能出现在读写第三方加密备份的路径上，参数一律取自该文件头部，派生密钥禁止参与自有 vault 的任何密钥派生或认证，且 `packages/vault` 不得依赖该路径。

### 3.1 压缩侧信道（CRIME / BREACH 类）的评估结论

"先压缩再加密"会让密文长度泄露明文的部分信息，这是 CRIME / BREACH 攻击的原理。**本项目评估后接受该风险**，因为成立条件全部不满足：

- 攻击者需要能**反复**让 App 以「自己选定的明文 + 受害者的秘密」一起加密，并**观测每次的密文长度**。
- 本 App 纯本地、无自建后端（[ADR-002](decisions.md#adr-002)），不存在可被攻击者驱动的加密预言机：vault 只在用户主动修改时重加密，攻击者无法注入选定明文，也无法观测密文长度。
- 唯一的远程交互是局域网配对迁移（§6），传输的是**已加密的 vault blob**，全程一次性、不重加密、不接受对端提供的明文片段。

因此不引入"关闭压缩"或"压缩前填充"这类对策——它们会增大文件、拖慢低端设备，却防不住本项目威胁模型里不存在的攻击者。**若将来引入任何形式的服务端加密或多设备增量同步，本结论必须重新评估。**

## 4. 跨端实现一致性（本项目最大技术风险）

三端使用不同的 Argon2id 实现：

| 端                      | 实现                                  |
| ----------------------- | ------------------------------------- |
| Web / 扩展 / Tauri 前端 | `hash-wasm`（WASM）                   |
| Android                 | argon2-jvm（JNI）                     |
| iOS                     | libsodium `crypto_pwhash`（Argon2id） |

**风险**：任一实现的参数解释、内存单位（KiB vs MiB）或输出编码存在偏差，就会导致"手机上加密的 vault 在插件里打不开"这类致命且难以定位的问题。

**强制缓解措施**（在 M0 阶段完成，不得推迟）：

1. 使用 Argon2 官方测试向量（**RFC 9106 §5.3** + libsodium 测试集）验证每端实现。Web 端因 `hash-wasm` 缺 `associatedData` 入参而采用「参考实现对照 + 生产配置比对」的等价论证链，详见 [testing.md §3.2](testing.md#32-已知答案测试kat先行)。
2. 建立跨端一致性测试：固定 `password / salt / m / t / p`，各端输出必须与**同一份共用参考向量**（置于 `packages/crypto`）字节级完全一致。
3. 明确并统一内存参数单位（本文档规定 `memoryKiB`，值 65536）。
4. 用一个真实的加密 vault 样本文件做三端互相解密的往返测试，纳入 CI。

**验证 gate 按端拆分**：

- **Web 端部分通过之前，不得开始 vault 层的任何实现工作。** Web 端部分指上述措施 1（KAT 与等价论证链）、2（与共用参考向量字节一致）、3 在 Web Provider 上落地；措施 4 的三端互相解密需等设备就绪。
  → **本 gate 已于 2026-09-24 达成**（GitHub Issue #2），vault 层实现已解锁。措施 4 的"真实文件往返"落点在根级 `test/`，见 [testing.md §3.3](testing.md#33-生产参数下的三端比对)。
- **移动端部分（Android / iOS 与共用参考向量字节一致 + 措施 4 的三端往返）必须在 M3 开工前补齐。** 本 gate **仍然生效**，不因 Web 端达成而放宽。

拆分不削弱防护：两部分比对的是**同一份**参考向量，移动端并未降低标准，只是验证时点后移到具备真机条件时。拆分依据见 [roadmap.md M0](roadmap.md#m0--基础设施与技术验证--关键路径)。

## 5. MV3 解锁态管理

Chrome 扩展的 service worker 在 popup 关闭后会被回收（通常 30 秒空闲），解锁状态不能只放在 SW 内存中。

方案：

- DEK 存入 `chrome.storage.session`。该 API 仅存在于内存，浏览器关闭即清空，不会落盘。
- popup 打开时先从 `storage.session` 读取 DEK；读不到则要求输入主密码。
- 可选的空闲自动锁定：用 `chrome.alarms` 定时检查最后交互时间，超时则清除 `storage.session` 中的 DEK。
- **禁止**将 DEK 或主密码写入 `chrome.storage.local`（会落盘）。`local` 只存加密后的 vault blob。

注意：`chrome.storage.session` 的默认访问级别是 `TRUSTED_CONTEXTS`，扩展页面可访问，content script 不可——这正是我们想要的。不要为了"方便"改成 `ALL_CONTEXTS`。

## 6. 迁移通道安全（局域网配对）

手机 → 扩展的局域网传输属于高风险路径（同一网络内可能存在攻击者）。

设计：

1. 手机生成一次性 ECDH（X25519）临时密钥对，启动仅监听局域网地址的 HTTP 服务，配对完成后立即关闭。
2. 手机屏幕显示二维码，内容为 `IP:port + 临时公钥 + 6 位配对码`。
3. 扩展侧生成自己的临时密钥对，完成 ECDH 协商；配对码用于**认证**（对协商出的会话密钥做 HKDF 时混入配对码，并交换认证标签），防止局域网内其他设备抢连。
4. 传输内容为已加密的 vault blob（DEK 包裹态），**不传输明文，也不传输主密码**。
5. 全程一次性：不持久化配对信息，不留存会话密钥，传输完成即销毁。

**不能依赖 mDNS**：浏览器扩展无法做 mDNS 服务发现，必须靠二维码或手输 IP。设计时不要假设自动发现能力。

## 7. 运行时防护

| 防护项        | 措施                                                                                                               | 优先级       |
| ------------- | ------------------------------------------------------------------------------------------------------------------ | ------------ |
| 截屏/录屏泄露 | Android `FLAG_SECURE`；iOS 监听截屏事件遮罩；提供设置开关                                                          | 建议默认开启 |
| 最近任务卡片  | Android 在进入后台时覆盖遮罩层                                                                                     | 建议默认开启 |
| 剪贴板残留    | 复制验证码后 30–60 秒自动清空（可关闭）                                                                            | 默认开启     |
| 空闲自动锁定  | 可配置超时（默认 60 秒），锁定后需重新解锁                                                                         | 默认开启     |
| 内存中的明文  | `Uint8Array` 形态的密钥与中间字节用毕 `fill(0)`（含异常路径）；解析后的字符串无法清零，靠最小化存活期缓解，见 §2.2 | 强制         |
| 日志泄露      | 全局禁止输出 secret / DEK / 主密码 / 验证码；封装 logger 做字段脱敏                                                | 强制         |
| 崩溃上报      | 不采集 vault 内容；若接入崩溃上报，须做敏感字段过滤                                                                | 强制         |

> 注：用户在需求确认中选择的是「强制主密码 + 可选生物识别」，未选「自动锁定与防截屏加固」。上表中标注"建议默认开启"的项属于加固增强，实现时作为设置项提供，不阻塞 M3 验收。

## 8. 导入路径的输入信任边界

导入文件是**完全不可信输入**。要求：

- 所有解析器为纯函数，无副作用，不做动态代码执行（禁 `eval` / `new Function` / 动态 `require`）
- 对 protobuf、JSON、CSV 解析设置长度与嵌套深度上限，防止内存耗尽
- 单条目解析失败不中止整体导入，收集错误后呈现"部分成功"报告
- 解析器纳入模糊测试（见 [testing.md](testing.md)）
- 导入前展示摘要（条目数、来源格式、失败数），经用户确认后才写入 vault

## 9. 明确不做的事

- 不做云同步、不做账号体系、不上传任何数据
- 不做多用户 / 共享密钥库
- 不在服务端做任何计算（因为没有服务端）
- 不支持弱化的"无密码 vault"（见 [ADR-006](decisions.md#adr-006)）
- V1 不支持硬件密钥派生（架构上预留，见 §2）
